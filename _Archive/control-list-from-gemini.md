Engineering Specification of the SecureGuide Knowledge Extraction, Classification, and Validation Engine: Unified Security Artifact Classification Model (USACM v2.2.1) and Security Domain Taxonomy (SDT v2.2.1)Architectural Paradigm of Semantic Compliance AutomationModern cyber-physical systems and enterprise cloud environments suffer from a critical operational mismatch known as compliance lag. While infrastructure configurations and threat landscapes change continuously, compliance monitoring historically relies on point-in-time manual audits and static Word or Excel documents. This manual approach is slow, prone to human error, and fails to scale in heterogeneous cloud environments where API misconfigurations, database drift, and identity vulnerabilities expose assets to exploitation. When regulatory frameworks or service terms undergo updates, mapping those changes back to active system controls introduces a significant non-conformity window, leaving organizations exposed to security breaches and legal penalties.To address this challenge, the SecureGuide Cybersecurity Knowledge Extraction, Classification, Relationship Mapping, and Validation Engine establishes a continuous compliance-as-code automation paradigm. Operating as a multi-pass parsing and semantic mapping compiler, the SecureGuide engine converts unstructured regulatory mandates, standards, threat intelligence reports, and technical configurations into a structured, mathematically verifiable graph of security artifacts. By formalizing policy rules using the Unified Security Artifact Classification Model (USACM v2.2.1) and the Security Domain Taxonomy (SDT v2.2.1), the engine models regulatory text as machine-interpretable data. This allows organizations to run automated validation queries and continuously trace technical controls back to their authoritative regulatory origins.The Multi-Pass Extraction PipelineThe core operational flow of the SecureGuide engine is structured as an eight-pass compilation pipeline designed to maximize recall while maintaining precise, traceable classification. Each pass operates on the syntax and semantics of the ingested document, progressively building a validated directed graph of security nodes and relationships.[Unstructured Source]

PASS 1 — Document Structure AnalysisThe engine begins by parsing the document layout to establish the structural hierarchy, identifying sections, subsections, table structures, numbered clauses, bullet points, and appendices. Simultaneously, it extracts metadata (such as issuing authorities, publication versions, effective dates, and review cycles) and runs named entity recognition (NER) to locate referenced systems, technologies, roles, and frameworks.The engine scans for specific normative keywords to assess the obligation level of each statement. Arabic equivalents are evaluated alongside English terms to support multi-regional compliance sources:Mandatory (OBL-MND): "must", "shall", "is required to", "is obligated to", "is prohibited from", "may not", "must not", "يجب", "يتعين", "يلزم", "يحظر", "لا يجوز".Recommended/Conditional (OBL-REC): "should", "is recommended to", "where applicable", "as appropriate", "when required", "ينبغي", "يوصى", "عند الاقتضاء", "حسب الحاجة".Optional (OBL-OPT): "may", "can", "is permitted to", "يجوز", "يمكن".PASS 2 — Explicit Artifact ExtractionThe engine scans the structured text to directly isolate explicitly stated security components, mapping them to candidate USACM artifact types. This pass focuses on extracting directly stated requirements, policies, operational procedures, assets, known threat actions, and assigned compliance roles.PASS 3 — Atomic DecompositionTo avoid overly broad and un-verifiable nodes, the engine decomposes compound sentences containing multiple independent duties into separate, atomic artifacts. For example, a directive stating "Administrators must enable MFA, review privileged access quarterly, and retain access evidence for one year" is split into several distinct nodes:A requirement node (ART-REQ) mandating MFA for administrative access.A control node (ART-CTR) implementing phishing-resistant MFA authentication.A process node (ART-PRO) for conducting periodic access reviews.A metric node (ART-MET) defining a quarterly review frequency.An evidence node (ART-EVD) representing the generated access review records.A standard node (ART-STD) enforcing a one-year retention period for compliance logs.PASS 4 — Controlled Implicit Artifact DiscoveryThe engine infers unstated but logically necessary artifacts established by the context of the source text. This is strictly constrained to prevent the fabrication of unsupported organizational details, systems, or products. For example:An explicit administrative task implying a corresponding process owner role (ART-OWN).A logging or audit requirement implying a necessary proof object (ART-EVD).An explicitly stated performance target or frequency implying a tracking metric (ART-MET).An insecure default configuration implying a underlying system vulnerability (ART-VUL).Every inferred node is explicitly marked with an extraction basis of INFERRED_FROM_SOURCE and assigned a lower classification confidence score to ensure it is routed for human validation.PASS 5 — Entity and Relationship ExpansionOnce the initial list of artifacts is built, the engine inspects each node to resolve referenced entities and expand them into standalone nodes. If an extracted security control mentions that it protects an "active database" against "SQL injection" using a "web application firewall," the engine generates separate nodes:An asset node (ART-AST) representing the database.A threat node (ART-THR) representing SQL injection attacks.A control node (ART-CTR) representing the web application firewall.These nodes are then linked via semantic relationships to represent their real-world interactions.PASS 6 — Cross-Section ReconciliationThe engine compares the generated artifacts across all sections to identify duplicate entries, repeated controls, and hierarchical parent-child relationships. The engine does not merge similar items unless their action, scope, expected outcome, and target population are equivalent. If a policy clause conflicts with a technical control (such as a local privacy policy conflicting with a SaaS provider's data residency terms), the engine preserves both nodes, links them via a conflict relationship (REL-CNF), and flags the conflict for human review.PASS 7 — Coverage Gap CheckPrior to finalization, an internal validation sweep confirms that every normative sentence in the source text has mapped to at least one valid artifact. Any text block that does not yield a valid artifact is documented in an unresolved_candidates array, along with the possible classifications and a recommended action for human operators.PASS 8 — Validation and FinalizationIn the final pass, the engine validates all extracted data against the USACM schema rules and the SDT security domain assignments. The engine calculates an overall classification confidence score, formats the validated structures, and generates the final output.The USACM v2.2.1 Ontological Schema & Artifact TypesThe Unified Security Artifact Classification Model (USACM v2.2.1) defines 22 distinct artifact types. This precise taxonomy prevents semantic ambiguity and ensures that compliance artifacts are classified based on their functional role rather than their phrasing.A common issue in manual mapping is classifying a policy statement as a control simply because it contains mandatory language, or confusing a process with a step-by-step procedure. The USACM schema avoids this by establishing strict boundaries:Requirements (ART-REQ) vs. Controls (ART-CTR): A requirement describes the mandatory security objective that must be achieved, while a control describes the technical, physical, or organizational mechanism used to enforce that requirement.Processes (ART-PRO) vs. Procedures (ART-PRC): A process outlines a repeatable, high-level operational flow with inputs, tasks, and outputs. A procedure provides detailed, step-by-step instructions for executing those tasks.Metrics (ART-MET) vs. Evidence (ART-EVD): A metric represents a formulaic value, threshold, or target used to measure performance. Evidence represents a static proof object demonstrating that a control was executed at a specific point in time.Threats (ART-THR) vs. Vulnerabilities (ART-VUL) vs. Risks (ART-RSK): A threat represents an external actor, condition, or attack technique capable of causing harm. A vulnerability represents an internal weakness, configuration defect, or missing safeguard. A risk represents the potential adverse outcome that occurs when a threat exploits a vulnerability, characterized by its likelihood, business impact, and mitigation options.Table 2: USACM v2.2.1 Reference definitions represent ideal, static security baselines, whereas operational states capture the actual, point-in-time configuration of the system.The engine enforces this separation by initializing all master catalog attributes with standardized default values:implementation_status is initialized to STS-NOT-APPLIED.verification_status is initialized to VER-NOT-VERIFIED.effectiveness is initialized to EFF-UNKNOWN.exception_status is initialized to EXC-NONE.These initialization values are explicitly marked with a field provenance of DEFAULT_OPERATIONAL_VALUE.When the engine ingests real-time telemetry (such as vulnerability scan reports or system configurations), it records those findings within an independent observed_operational_state metadata block. This prevents dynamic telemetry from overwriting the pristine baseline catalog.Every attribute within the USACM schema is assigned a strict field_provenance tag to track its origin and prevent unverified inferences from being presented as established facts:EXPLICIT: Direct, verbatim statements extracted from the source document.NORMALIZED: Sourced directly from the text but converted to standard schema values.INFERRED_FROM_SOURCE: Logically deduced from explicit source context, such as inferring an unstated asset owner.CONTROLLED_SUGGESTION: Best-practice recommendations generated by the engine that are not explicitly stated in the source text.DEFAULT_OPERATIONAL_VALUE: SecureGuide engine initialization values used for state separation.Automated Quality Control, Confidence Estimation, and Human RoutingTo ensure accuracy, the engine calculates a classification confidence score ($C$) for every extracted artifact. This score is computed based on the clarity of the artifact boundaries, the explicit support in the source text, the completeness of the required fields, and any ambiguity regarding domain or type assignments.The engine uses this score to automate its quality control and human routing workflows:$C \ge 0.90$ (AIR-AUTO-ACCEPTED): The artifact is automatically approved and committed to the graph. Human review is bypassed unless a critical schema error is detected.$0.75 \le C \le 0.89$ (AIR-AUTO-ACCEPTED with Warnings): The artifact is committed to the graph, but any minor uncertainties are logged in a review_notes field for visibility.$0.60 \le C \le 0.74$ (AIR-HUMAN-REVIEW): The artifact is flagged for manual review, requiring human validation before being committed.$C < 0.60$ (AIR-HUMAN-REVIEW with Red Flags): The artifact is routed for manual validation. The engine logs the specific ambiguities, lists any rejected alternatives, and prompts the operator for input.The engine also maps priority levels (priority) to explicit priority weights (priority_weight) to help teams focus their remediation efforts:PRI-CRITICAL is assigned a weight of 10.PRI-HIGH is assigned a weight of 7.PRI-MEDIUM is assigned a weight of 4.PRI-LOW is assigned a weight of 1.These weights allow the engine to prioritize and route issues dynamically. Standard simulation engines typically weight these paths using static CVSS scores, which can lead to a Contextual Reality Gap by ignoring host-specific operating system defenses.To resolve this, the Host Active Verification Engine (HAVE) deploys lightweight, safety-constrained host agents to run snapshot-isolated exploit trials. The SecureGuide engine ingested this HAVE telemetry, parsing the trials as empirical evidence (ART-EVD). Using the maximum likelihood estimation (MLE) of the Bernoulli trials, the engine calculated the contextual probability of compromise ($p$) as:$$\hat{p} = \frac{1}{n} \sum_{i=1}^{n} k_i$$[cite: 19]This value was extracted as a performance metric (ART-MET) and mapped to the target asset's risk node (ART-RSK). This active integration allowed the SDT to update its graph edge weights with real-world exploitability data, bridging the gap between simulated risk and operational reality.Case Study C: Compliance-as-Code via NIST OSCAL and AI GovernanceThe engine parsed the NIST SP 800-171 and NISTIR 8259A standards to automate compliance tracking for Controlled Unclassified Information (CUI) and IoT device security.The engine analyzed the unstructured standards, extracting explicit requirements and compiling them into machine-readable NIST OSCAL schemas.
