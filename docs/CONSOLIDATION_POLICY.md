# سياسة توحيد ودمج العناصر المتشابهة (SecureGuide Consolidation Policy)

> هذه السياسة تحدد كيف يحوّل SecureGuide العناصر الخام والمتشابهة من مصادر متعددة إلى عناصر canonical موحدة، مع حفظ النسب الكامل للمصادر، ودون حذف السجلات الأصلية أو كسر USACM/SDT.

## 1. الهدف

الهدف ليس تحويل كل سجل خام إلى عنصر نهائي مستقل، بل بناء كتالوج SecureGuide أوضح وأقل تكراراً:

> **عدة مصادر متشابهة يمكن أن تدعم عنصر SecureGuide واحداً، بشرط حفظ كل مصدر ومبرر المطابقة.**

تنطبق هذه السياسة على:

- ضوابط متشابهة من أطر مختلفة.
- ضوابط تحمل المعنى نفسه بصياغات مختلفة.
- عناصر متداخلة يمكن ربطها بعلاقات بدلاً من دمجها.
- مراجعات Excel/CSV أو Curation Workbook التي تقترح الدمج أو التحسين.

## 2. المبادئ الحاكمة

1. **USACM وSDT أولاً**
   العنصر الموحد يجب أن يحتفظ بنوع USACM واحد، ومجال SDT واحد، ومجال فرعي واحد. أي سياق إضافي يذهب إلى tags أو extensions.

2. **لا حذف للسجلات الخام**
   `raw_artifacts` يبقى محفوظاً. الدمج لا يعني حذف المصدر، بل ربطه بعنصر canonical أو مجموعة تكافؤ.

3. **النسب قبل الاقتباس**
   حفظ `source_document`, `source_version`, `source_section`, `raw_artifact_id`, و`mapping_strength` أهم من نسخ النص الأصلي.

4. **التضمين مساعد لا حاكم**
   التشابه الدلالي يقترح المرشحين فقط. قرار الدمج النهائي يعتمد على المعنى، النطاق، النوع، المجال، وقابلية التحقق.

5. **المرونة دون فوضى**
   يمكن قبول tags أو aliases أو proposed values بسهولة. أما إضافة نوع USACM أو مجال SDT جديد فتتم كامتداد موثق، لا كتعديل مباشر عشوائي.

## 3. أنواع قرارات التوحيد

| القرار | المعنى | النتيجة |
|---|---|---|
| `CANONICALIZE` | عدة مصادر تدعم مفهوماً أمنياً واحداً | إنشاء/تحديث عنصر SecureGuide واحد مع mappings متعددة |
| `EQUIVALENCE_GROUP` | العناصر متكافئة تقريباً لكن يفضل إبقاؤها منفصلة | إنشاء مجموعة تكافؤ وتحديد canonical عند الحاجة |
| `CROSSWALK_ONLY` | يوجد تشابه أو تغطية جزئية، لكن لا يصح الدمج | إنشاء `framework_mappings` بقوة مناسبة |
| `RELATE_ONLY` | العلاقة منطقية لكن ليست تكافؤاً | استخدام `artifact_relationships` مثل REL-SAT أو REL-SUP أو REL-IMP |
| `KEEP_SEPARATE` | التشابه لفظي أو سطحي | إبقاء العناصر منفصلة |
| `DEPRECATE_DERIVED` | عنصر مكرر داخلياً بعد التوحيد | تعليم العنصر كـDEPRECATED مع حفظ النسب، دون حذف |

## 4. متى ندمج؟

يجوز الدمج عندما تتفق العناصر في معظم هذه النقاط:

1. الغرض الأمني الأساسي واحد.
2. نوع USACM المتوقع واحد أو متوافق.
3. المجال والمجال الفرعي SDT متطابقان أو يمكن حسمهما بثقة.
4. نطاق التطبيق قريب بما يكفي لصياغة عنصر عام واضح.
5. طريقة التحقق أو الدليل المتوقع متقارب.
6. لا يوجد فرق جوهري في الإلزام أو المستوى يجعل أحد العناصر متطلباً والآخر إجراءً تفصيلياً.

أمثلة مناسبة للدمج:

- عدة مصادر تطلب جرد الأصول التقنية.
- عدة مصادر تطلب مراجعة صلاحيات المستخدمين المميزين.
- عدة مصادر تطلب منع كلمات المرور الافتراضية.

## 5. متى لا ندمج؟

لا يتم الدمج إذا كان التشابه يخفي اختلافاً جوهرياً:

1. أحد العناصر متطلب (`ART-REQ`) والآخر إعداد تقني محدد (`ART-CFG`).
2. أحدهما يتناول الهوية (`SD-03`) والآخر يتناول hardening البنية (`SD-04`).
3. أحدهما دليل (`ART-EVD`) والآخر ضابط (`ART-CTR`).
4. أحدهما خاص بتقنية محددة لا يصح تعميمها.
5. التشابه نصي فقط، لكن الهدف أو النطاق مختلف.

في هذه الحالات استخدم mapping أو relationship بدلاً من الدمج.

## 6. بناء العنصر canonical

عند إنشاء عنصر موحد، يجب إنتاج صياغة SecureGuide أصلية وفق [`AUTHORING_POLICY.md`](AUTHORING_POLICY.md):

- `title_en`: عنوان واضح وقصير.
- `definition_short_en`: تعريف مختصر لا ينسخ النص الأصلي.
- `definition_full_en`: شرح عملي يوضح الغرض والنطاق والحد الأدنى والتحقق.
- `objective_en`: نتيجة أمنية واحدة.
- `type`: قيمة USACM واحدة.
- `primary_domain` و`sub_domain`: قيمة SDT واحدة لكل منهما.
- `classification_confidence` و`classification_rationale`.
- mappings لكل مصدر ساهم في العنصر.

لا يستخدم العنصر canonical نصاً أصلياً كاملاً من ISO أو CIS أو PCI أو غيرها. المصدر يبقى في raw/lineage.

## 7. قوة المطابقة بين المصدر والعنصر الموحد

كل مصدر مرتبط بالعنصر الموحد يجب أن يحمل `mapping_strength`:

| القوة | الاستخدام |
|---|---|
| `DIRECT` | المصدر يطابق العنصر الموحد بشكل مباشر |
| `INDIRECT` | المصدر يدعم المعنى لكن بصياغة أو نطاق مختلف |
| `PARTIAL` | المصدر يغطي جزءاً من العنصر أو العنصر يغطي جزءاً منه |
| `INFORMATIVE` | المصدر مفيد كمرجع فقط |

أي mapping غير `DIRECT` يحتاج rationale مختصر.

## 8. Curation Workbook

عند تصدير الكتالوج إلى Excel/CSV للمراجعة:

- لا يغير المراجع `artifact_id` أو `raw_artifact_id`.
- يمكنه اقتراح `canonical_group_id` أو `merge_action`.
- يمكنه تعديل الصياغة والتصنيف من القيم المعتمدة.
- يمكنه إضافة proposed tags أو aliases.
- لا يمكنه إضافة USACM/SDT أساسي جديد مباشرة.

عند الاستيراد الراجع:

1. تدخل التعديلات إلى staging.
2. يعرض التطبيق تقرير فروقات.
3. تطبق قواعد USACM/SDT والتحقق من sub-domain.
4. يعتمد المستخدم التعديلات كلها أو جزئياً.

## 9. التعلم والدروس المستفادة

يجب أن يتحسن الدمج بمرور الوقت دون بناء نظام مؤسسي ثقيل. لذلك تحفظ الدروس كقواعد عملية بسيطة:

| الدرس | مثال | الأثر |
|---|---|---|
| نمط تصنيف متكرر | عناصر "inventory" غالباً SD-02.01 | تحسين prompt التصنيف |
| نمط دمج متكرر | Asset inventory من CIS/NIST/NCA يندمج في عنصر واحد | تحسين قواعد الترشيح |
| خطأ متكرر | خلط `ART-CTR` مع `ART-CFG` في hardening settings | إضافة قاعدة تحذير |
| استثناء متكرر | Cloud IAM يصنف SD-03 لا SD-04 | تعزيز tie-breakers |

يمكن حفظ هذه الدروس في ملف بسيط أو جدول لاحق مثل `curation_lessons`، لكن لا يلزم بناء workflow موافقات معقد.

## 10. قواعد تحسين السياسة

تُحدَّث هذه السياسة عندما تظهر إحدى الحالات التالية:

1. تكرار تصحيح بشري لنفس النمط.
2. رفض متكرر لاقتراحات الدمج من النموذج.
3. ظهور مصدر جديد له بنية مختلفة فعلاً.
4. وجود غموض لا تحسمه USACM/SDT بوضوح.
5. نتائج Golden Dataset تتراجع بعد تعديل القواعد.

أي تحديث يجب أن يضيف قاعدة عملية أو مثالاً، لا نصاً نظرياً عاماً.

## 11. فحوص الاعتماد قبل النشر

قبل نشر عنصر موحد:

1. له source lineage واحد على الأقل.
2. له mapping strength لكل مصدر.
3. لا توجد مصادر مدمجة بدون rationale عند `PARTIAL` أو `INDIRECT`.
4. لا يحتوي نصاً أصلياً مطولاً من المصدر.
5. له USACM type وSDT domain/sub-domain صالح.
6. إن كانت الثقة `<= 0.70`، يبقى `AIR-HUMAN-REVIEW` ولا يُنشر آلياً؛ لا يمنع ذلك وحده `MINIMUM_VALID`.
7. إذا كان ضمن equivalence group، فهناك canonical واضح أو سبب لإبقائه كعضو فقط.
